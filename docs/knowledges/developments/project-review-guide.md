## Overview

プロジェクトレビューとは、基本計画から設計・プログラミング・運用テストに至る各フェーズにおいて、関係者が集まり成果物（設計書、仕様書、ソースコード等）の疑問点、曖昧な点、潜在的な欠陥を洗い出して評価・改善するための協議および評価プロセスのことです。

プロジェクトの目的達成、品質向上、標準化・規制適合の確認、並びにプロジェクト運用上の意志決定や「学び（Lessons Learned）」の抽出を目的として実施されます。ソフトウェア・システム開発においては、**IEEE 1028** などの国際標準に基づき、目的や厳格さ（フォーマリティ）に応じた標準的な分類が用いられます。

## Phases and environments

プロジェクトレビューは、システム開発ライフサイクルの以下のような各フェーズ・検証環境において実施されます。

- **要件定義・基本設計フェーズ（Requirements & Architecture Review Environment）**
  - 業務要件定義書、システム構成図、非機能要件定義書などの論理整合性や漏れを検証する環境。
- **詳細設計・仕様策定フェーズ（Detailed Design Review Environment）**
  - DB設計書、API仕様書、画面遷移図、クラス図などの詳細設計成果物をレビューする環境。
- **実装・プログラミングフェーズ（Implementation & Code Review Environment）**
  - ソースコード、各種設定ファイル、単体テストコードを対象に、コーディング規約遵守や潜在バグを検出する環境（Git/GitHub等を用いたPull Requestベースの環境を含む）。
- **統合・システムテストフェーズ（Integration & System Testing Review Environment）**
  - 結合テスト計画書、テストケース、障害分析レポート、リリース判断基準などを確認・検証する環境。
- **プロジェクト完了・マイルストーン評価フェーズ（Post-Project & Gate Review Environment）**
  - プロジェクト終了時またはフェーズ切り替え時に、進捗・コスト・成果物品質・運用引き継ぎ項目を総括・判定する環境。

## Review Types (IEEE 1028 Standard)

IEEE Std 1028 で定義されている5つの標準的なレビュー区分です。目的および実施主体によって分類されます。

| Review Category | Description (概要と特徴) | Key Focus Areas (主な対象・焦点) |
| :--- | :--- | :--- |
| **Management Review** | プロジェクトの進捗、リソース割り当て、進捗計画と実績の乖離を確認し、目標達成のためのマネジメント手法を評価するレビュー。 | 進捗状況、マイルストーン達成度、リソース不足の解決、リスク対策、スコープ変更判断。 |
| **Technical Review** | 専門知識を持つ技術者が集まり、成果物が技術的な要件や設計基準に沿っているか、技術的妥当性を評価するレビュー。 | アーキテクチャの整合性、技術的実現可能性、技術標準への準拠性、設計妥当性。 |
| **Inspection** | 最も体系的かつ厳格なピアレビュー。作成者以外の主導者（モデレーター）を立て、明確な役割分担とチェックリストを用いて多段階プロセスで欠陥を抽出する。 | 早期の欠陥検出、コーディング規約・設計基準の遵守、定量的品質分析。 |
| **Walkthrough** | 成果物の作成者（レビューイ）が主導し、参加者（レビューア）に内容を説明しながらコメントや意見を求めていくレビュー。 | 概念やロジックの共有、初期段階でのアイデア集め、作成者の意図の共有。 |
| **Audit** | 独立した評価者（監査人）が、製品やプロセスが組織の標準、ガイドライン、国内法、国際規格（ISO等）、契約上の要件に沿っているかを評価する。 | 法的規制遵守、標準ガイドライン適合性、プロセス品質監査、契約適合性。 |

## Operational Techniques & Methods

作業成果物（設計書やソースコード等）の欠陥検出や確認を行う際、適用される具体的な手法・アプローチの一覧です。

### Comparison list of methods/techniques

| Method / Technique | Description (特徴と解説) | Pros & Cons (メリット・デメリット) |
| :--- | :--- | :--- |
| **Inspection**<br>(インスペクション) | 役割（モデレーター、レポーター、記録係等）を定義し、事前準備・レビュー会議・修正確認まで厳格な手続きを踏んで実施する。 | **メリット:** 欠陥検出率が非常に高く、品質向上効果が大きい。<br>**デメリット:** 事前準備や会議コスト（工数）が高い。 |
| **Team Review**<br>(チームレビュー) | 複数のメンバーが集まり、事前に提示された課題や成果物に対して問題解決や合意形成を図るために実施される。 | **メリット:** チーム全体の合意形成と意識共有が容易。<br>**デメリット:** 日程調整が必要で、参加者の発言度合いに偏りが出ることがある。 |
| **Walkthrough**<br>(ウォークスルー) | 作成者が中心となって成果物をセクションごとに順を追って説明し、参加者からフィードバックを受ける。 | **メリット:** 導入ハードルが低く、教育効果も高い。<br>**デメリット:** 作成者主導のため、作成者のバイアスによって欠陥を見逃す可能性がある。 |
| **Pair Review**<br>(ペアレビュー) | 作成者と1名のレビューアがペアになり、リアルタイムで成果物を確認・修正する（ペアプログラミングやペアデザインなど）。 | **メリット:** フィードバックが即座に行われ、ノウハウ共有・育成効果が高い。<br>**デメリット:** 指摘の精度がレビュアー個人のスキルに依存する。 |
| **Pass-around**<br>(パスアラウンド) | メールやグループウェア、Pull Requestなどを活用し、成果物のコピーを複数人に配布して非同期でフィードバックをもらう。 | **メリット:** 時間や場所を縛られず、ミーティング枠の確保が不要。<br>**デメリット:** 議論が深まりにくく、対面での問題解決に向かない場合がある。 |
| **Ad-hoc Review**<br>(アドホックレビュー) | 計画的な会議ではなく、必要に応じて隣の同僚やオンラインのメンバーに即座に確認してもらう不定期・簡易的なレビュー。 | **メリット:** オーバーヘッドが無く、即座に疑問を解消できる。<br>**デメリット:** 記録が残らず、体系的な欠陥検出には向かない。 |

## Strategic & Organizational Reviews

プロジェクトの継続判断、ステークホルダー間の情報共有、組織的学習を目的として実施されるレビュー手法です。

- **Educational Review（教育レビュー）**
  - プロジェクトで使用する技術トピックやビジネスドメイン知識について、チームメンバーやステークホルダーの知識レベルを引き上げるために実施されるレビュー。
- **Management Review / Gate Review（マネジメントレビュー／ゲートレビュー）**
  - 上級管理職や判定委員会に対して情報を提供し、フェーズの通過（Stage-Gate）、製品リリース、プロジェクトの継続または中止、リソース再配分、スコープ変更を決定するための戦略的レビュー。
- **Peer Review（ピアレビュー）**
  - 役職や立場に関わらず、同僚（ピア）同士で成果物の欠陥検出や改善の機会を探すためのレビュー全般。
- **Status Review（ステータスレビュー）**
  - プロジェクトマネージャーとチームメンバーが、マイルストーンに対する進捗、発生した課題（Issue）、リスクの識別・制御状態を定期的に確認するレビュー。
- **Project End Review / Retrospective（プロジェクト終了レビュー／振り返り）**
  - プロジェクトまたは特定フェーズの終了直後に実施し、成功要因や反省点を洗い出して将来のプロジェクトに活かす「教訓（Lessons Learned）」を抽出するレビュー。

## Process Flow of Formal Reviews

フォーマルなレビュー（インスペクションやテクニカルレビュー等）を実行する際の基本的なステップです。

```text
[ 1. Planning ] ➔ [ 2. Preparation ] ➔ [ 3. Review Meeting ] ➔ [ 4. Rework & Tracking ] ➔ [ 5. Closure ]
```

1. **Planning（計画・準備）:** レビューの対象・範囲・適用手法を決定し、ロール割り当てと資材配付を行う。
2. **Preparation（事前準備）:** 参加者が個別に成果物を読み込み、疑問点や欠陥候補を事前に洗い出す。
3. **Review Meeting（レビュー会議）:** 提出された指摘事項を協議し、欠陥の認定および修正方針の合意を行う。
4. **Rework & Tracking（手戻り・修正追跡）:** 作成者が指摘事項に基づいて成果物を修正し、追跡・確認する。
5. **Closure（完了・集計）:** 修正内容の最終確認を行い、検出率やメトリクスを記録してレビューを完了する。
