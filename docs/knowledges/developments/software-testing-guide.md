# Software Testing Methods and Techniques Guide

## Overview

ソフトウェアテストは、ソフトウェア開発ライフサイクル（SDLC）において、プロダクトの品質、正確性、完全性、およびセキュリティを評価するための必須のプロセスです。テストを実施することで、ソフトウェアが機能要件を満たしているか、多様な負荷環境下で安定して動作するか、および境界値や例外的な入力に対しても適切に対応できるか検証します。

## Phases and Environments

- **Phase 1: 単体テスト（Unit Testing）**（対象: 関数、クラス、コンポーネント単位のモジュール）
- **Phase 2: 結合テスト（Integration Testing）**（対象: モジュール間のインターフェースおよびデータ連携）
- **Phase 3: システムテスト（System Testing）**（対象: システム全体の機能・非機能要件およびエンドツーエンドの動作）
- **Phase 4: 受入テスト（Acceptance Testing）**（対象: ユーザー要件への適合性および本番環境での運用性）

## Testing Approaches

### White-Box Testing

- **定義:** システムの内部構造、アーキテクチャ、ソースコードを熟知した状態で行う構造的テスト手法です。
- **目的:** 内部ロジックの正確性を検証し、制御フロー上のすべてのパスが正しく実行されること、および潜在的な脆弱性や論理エラーを検出します。
- **主な用途:** 単体テスト、結合テスト、静的コード解析。

### Black-Box Testing

- **定義:** システムの内部構造や実装コードに関する知識を持たずに、外部仕様に基づいて行う仕様ベース（振る舞い）のテスト手法です。
- **目的:** 指定された入力に対する出力が、要求仕様書通りの期待値と一致するかを検証します。
- **主な用途:** システムテスト、受入テスト、UI・機能テスト。

### Gray-Box Testing

- **定義:** ホワイトボックスとブラックボックスを組み合わせたハイブリッド手法です。テスターはシステム内部の限定的な情報（データベース構造やAPI仕様書など）を保持した状態でテストを実施します。
- **目的:** システムの内部設計を念頭に置きつつ、ユーザー視点での振る舞い検証を効率的に進めます。

## White-Box Testing Techniques (Code Coverage)

コードカバレッジ（網羅率）は、テスト実行によってソースコードがどの程度実行されたかを測定する指標です。

```text
       [ ソースコード構造 ]
                 │
    ┌────────────┼────────────┐
    ▼            ▼            ▼
 ステートメント   ブランチ     コンディション
 カバレッジ(C0) カバレッジ(C1) カバレッジ(C2)
```

### Statement Coverage ($C_0$)

- **概念:** ソースコード内のすべての実行可能命令文（ステートメント）が、少なくとも1回は実行されることを保証する指標です。
- **計算式:**

$$
\text{ステートメントカバレッジ } (C_0) = \left( \frac{\text{実行された命令文の数}}{\text{全実行可能命令文の総数}} \right) \times 100\%
$$

- **制限事項:** 分岐処理（例: `else` 側の未処理など）を評価しないため、制御フロー上の問題を見逃す可能性があります。

### Branch / Decision Coverage ($C_1$)

- **概念:** `if` や `switch` などの条件分岐において、すべての判定結果（真 `True` / 偽 `False`）が少なくとも1回は実行されることを保証します。
- **計算式:**

$$
\text{ブランチカバレッジ } (C_1) = \left( \frac{\text{実行された分岐結果の数}}{\text{全分岐結果の総数}} \right) \times 100\%
$$

- **特長:** $C_1$ カバレッジを100%達成すると、自動的に $C_0$ カバレッジも100%達成されます ($C_1 \implies C_0$)。

### Condition Coverage ($C_2$)

- **概念:** 複合条件式に含まれる個々の独立した論理条件（サブ条件）が、それぞれ少なくとも1回は `True` と `False` の両方の値を評価することを保証します。
- **例:** `if (A or B)` という条件式の場合、$A$ と $B$ のそれぞれが単独で `True` と `False` になるテストケースを作成します。

### Multiple Condition Coverage (MCC) & MC/DC

- **複数条件網羅 (MCC):** 条件式内のすべてのサブ条件の組み合わせパターンを網羅します。$n$ 個の条件がある場合、$2^n$ 個のテストケースが必要となります。
- **修正条件判定網羅 (MC/DC):** 航空機や自動車など安全性が極めて重視されるドメインで利用される手法です。各条件が他の条件の影響を受けずに単独で判定結果を変更できることを確認し、$n+1$ 個のテストケースで網羅性を確保します。

## Black-Box Testing Techniques

### Equivalence Partitioning

- **概念:** 入力データを、システムが同様に処理すると想定される同値グループ（パーティション）に分割し、各グループから代表値を選定してテストを行います。
- **メリット:** テストの偏りをなくし、同等の網羅性を保ちながらテストケース数を最小化します。
- **具体例:**
  - 条件範囲: $1 \le \text{年齢} \le 100$
  - 有効パーティション: $15$（$[1, 100]$ の範囲を代表）
  - 無効パーティション: $-5$（$< 1$ の範囲を代表）、$105$（$> 100$ の範囲を代表）

### Boundary Value Analysis (BVA)

- **概念:** 不具合が発生しやすい入力領域の「境界値（限界値）」に焦点を当ててテストを行う手法です。
- **検証する境界値の種類:**
  - 最小値 ($MIN$)
  - 最小値の直上 ($MIN+$)
  - 最小値の直下 ($MIN-$)
  - 最大値 ($MAX$)
  - 最大値の直下 ($MAX-$)
  - 最大値の直上 ($MAX+$)
- **具体例:** 有効範囲が $[1, 100]$ の場合、テスト対象の値は $0, 1, 2, 99, 100, 101$ となります。

### Decision Table Testing

- **概念:** 複数の入力条件とそれに応じたシステムの動作（出力）をマトリクス形式で整理し、複雑なビジネスロジックの網羅性を評価する手法です。
- **構成例:**

| 条件 / アクション | ルール 1 | ルール 2 | ルール 3 | ルール 4 |
| ----- | ----- | ----- | ----- | ----- |
| **条件 A:** 有効なユーザーか？ | Y | Y | N | N |
| **条件 B:** 正しいパスワードか？ | Y | N | Y | N |
| **アクション 1:** ログインを許可 | X | - | - | - |
| **アクション 2:** エラーを表示 | - | X | X | X |

### State Transition Testing

- **概念:** システムが過去の履歴や現在のステート（状態）に応じてどのように挙動を変更するかを検証します。状態遷移図や状態遷移表に基づいて、適切な状態遷移と不正な遷移のガードをテストします。

### Use Case Testing

- **概念:** ユースケース記述書に基づき、アクター（ユーザーや外部システム）とシステムとの一連のインタラクション（正常系シナリオおよび異常系・代替シナリオ）を検証するエンドツーエンドのテスト手法です。

## 5. Testing Types and Strategies

### Regression Testing

- **定義:** プログラムの修正、バグ改修、機能追加が行われた際に、その変更によって既存の正常な機能に予期せぬ悪影響（デグレード/退行）が生じていないかを確認するために全機能または影響範囲を再テストします。
- **実施方針:**
  - **フルレグレッション:** 大幅なアーキテクチャ変更時などに、すべてのテストケースを再実行します。
  - **絞り込みレグレッション:** ソースコンペアやコードの影響分析に基づき、修正箇所およびその波及範囲に限定して実行します。
  - **自動レグレッション:** CI/CDパイプラインに自動テストを組み込み、リポジトリへのコード追加時に継続的にテストを実行します。

### Source Comparison (Diffing)

- **定義:** 厳密には動的なソフトウェア実行テストではなく、バージョン管理システムやDiffツールを用いたソースコードの差分比較プロセスです。
- **目的:** 意図した修正箇所以外に不要な変更、コメントの消去、予期せぬコードの紛れ込みがないかを事前・事後に静的に確認します。

### Smoke and Sanity Testing

- **スモークテスト (Smoke Testing):** 新しいビルドが配布された際、主要な機能が正常に動作するかを浅く広く確認する初期検証テストです。
- **サニティテスト (Sanity Testing):** 特定の不具合修正や機能追加が期待通りに動作しているかを局所的に深堀りして確認する迅速な検証テストです。

## 6. Root Cause Analysis Methods

### The 5 Whys Methodology

- **概念:** 発生した問題に対して「なぜ（Why）？」を5回繰り返すことで、表面的な現象にとらわれず、問題の根本原因（Root Cause）に到達する分析手法です。
- **実践例:**
  1. *なぜアプリケーションがクラッシュしたのか？* $\to$ データベース接続がタイムアウトしたため。
  2. *なぜタイムアウトしたのか？* $\to$ DBコネクションプールが枯渇したため。
  3. *なぜコネクションが枯渇したのか？* $\to$ 接続が正しくクローズされていなかったため。
  4. *なぜクローズされなかったのか？* $\to$ 新しく追加されたモジュールに例外処理が不足していたため。
  5. *なぜ例外処理が抜け落ちていたのか？* $\to$ DB接続に関するコーディング規約のガイドラインが更新されておらず、開発チームに周知されていなかったため（**根本原因**）。

### Fishbone Diagram (Ishikawa)

- **概念:** 発生した不具合・品質課題を中心に置き、要因となる要素（人、プロセス、設備、環境など）を魚の骨の形のように体系的に整理・分析する視覚的手法です。
